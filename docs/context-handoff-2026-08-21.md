## 0. 铁律（一切设计都是它的推论）

> **数据库是历史，上下文是投影。** 数据库里每条消息永远保留，Context Assembly 只决定「这一次请求，把哪些历史发给模型」。摘要不删原文、冻结边界不重切、预算只是安全上限。

改代码时任何「要不要删历史 / 要不要改历史」的冲动，都是违反铁律的。

## 1. 一次请求，模型看到什么（当前真实状态）

```
system  stablePrompt +【背景纪律】           ← 稳定，缓存锚点①（cache_control 1h）
────────────────────────────────────────
frozen 前 frozen_rounds(默认10)轮原文       ← 字节级稳定，缓存锚点②（末条带 cache_control）
summary 摘要段（anchor + latest，各带断点） + 未覆盖的中间原文  ← 缓存锚点③
live   最近 live_rounds(默认15)轮原文
        └ 开头是动态注入块（时间/天气/【想起】/残留/岛桥，同轮≤3块）   ← 背景位 + 数量上限
她刚发的话（= live 最后一轮）               ← 永远是离响应最近的真实用户消息
────────────────────────────────────────
[share] 【分享的链接内容】                  ← 她贴链接且抓到了正文才有
[image] 【看图】规则                        ← 她发图才有
```

**缓存断点**（`cache_control: { type:'ephemeral', ttl:'1h' }`，OpenRouter 透传 Anthropic，**请求上限 4 个**）：
1. System Prompt（`server.js:2195`）
2. Frozen 段最后一条（`server.js:2206`）
3. Summary 段（`server.js:2211/2217`，anchor 和 latest 各一个）

之后是动态注入 + live + 当前消息——**都不带断点**，随请求变化，不污染前缀。

**代码位置**：核心组装 `buildModelContext()` 在 `server.js:2041`。最终消息 `messages` 在 `server.js:2322` 拼装：`[...frozenSection, ...summarySection, ...liveSection]`。当前用户消息在 `handleChat` 里**先入库**（`server.js:4924`）再调 `buildModelContext`（`server.js:4957`），所以它以「live 最后一轮」的身份存在，天然在注入块之后。share/看图 在 `server.js:4961/4993` 追加到末尾（属于当前输入的附属，不是背景）。

## 2. 缓存机制：为什么长这样

OpenRouter 前缀缓存：请求的开头若干字节如果和缓存过的一致，返回 `cache_read`（便宜）。TTL 1h。**前缀字节必须完全稳定**才能命中。

推论（三条红线，全部踩过坑）：
- **断点①~②（system + frozen）之间必须字节稳定**。任何可变内容（记忆/残留/时间/天气/工具结果）不得落进这个区间，否则前缀每次变，缓存全失效。
- **注入块不能用 system 角色**。OpenRouter 会把消息数组里的 system 角色**提升合并进顶层 system 参数** → system 前缀每次变 → 缓存失效。所以所有动态注入块都是 **user 角色**。
- **注入块不能用 assistant 角色**。会破坏 user/assistant 交替。

**代价（本次 bug 的根）**：因为注入块必须是 user 角色，它们从语法上和「她发的消息」没有区别。模型只能靠「前缀标记」+「系统【背景纪律】」来分辨「这是背景」vs「这是她刚说的话」。模型越弱，越分不清。

## 4. Bug 考古：前文跳转 / 不接上一句（完整经过）

### 4.1 症状（三个版本）
1. 程芥：「聊天一直左右跳转，思考链里会突然想到我的天气（虽然不说出来）」
2. 程芥：「聊得好好的，突然跳到前面提醒我喝水的事，直接不接上一句」
3. 程芥：「我刚刚发，他又会跳到之前的『修bug』，好像完全忘记我说过已经修完回来了，会让我先去修bug」

### 4.2 根因（不是单条 bug，是涌现）
活跃对话里，她消息**紧前面**可能同时杵着 4-6 个 user 角色注入块（时间/天气/【想起】/残留/岛桥/留言）。原来它们插在 `liveSection.length - 1`（**她消息正前方 = 显著性最高的位置**）。模型读到的是：

```
…
你刚发来的话
```

变成：

```
…
【当前时间】现在是深夜
【她那边】在下雨
【你心底想起的旧事】「她发过一张窗外夜景」
你刚发来的话
```

模型把注记块当「她刚说的话」，优先接注记内容，把她真实的最后一句晾在一边。「提醒喝水」「去修bug」都是这么冒出来的。**换省钱档模型后指令跟随弱一档，更分不清。**

### 4.3 已上修复（2026-08-21 已部署，全部在代码里）
1. **注入块全挪到 live 段开头**（背景位）——她最后那句成为无可争议的响应对象。注释见 `:2233-2238`。
2. **【背景纪律】强化**（`server.js:2091-2096`，stablePrompt 尾部追加）：
   - 点名所有注记段：`【历史背景】【背景记忆】【你心底想起的旧事】【登岛来路】【永无岛的回忆】【当前时间】【上次对话的余温】`——全是背景，不是她发来的。
   - **「你要回应的永远是她最后那句真实消息。注记段里哪怕写着【悬】、说还有没做完的事、或引了她早先离开时的话——那也只是背景里的牵挂，不是你现在要去办的指令，更不该抢在她当前的话前面被回应。她一句话里若明确喊你做事，你才去做。」**
   - 注意：删掉了旧版「她提起某件旧事，你自然接住」——这句宽松条款反而助长往回扯，是反例。
3. **残留 departure 时效框架**（`server.js:1580`）：`你上次走时说「…」——那是上次离开时的话，现在她已经回来了`。
4. **【想起】注意力收紧**：冷却 2→3（`ATTENTION_COOLDOWN_TURNS` `:1709`）、STOPWORD2 口水词过滤（`topicHits` `:1667`）、前缀改「是你自己的记忆，不是她发来的」。
5. **摘要段改按需注入**：`shouldInjectSummary = isFirstTurn || resumeGap`（`:2106`）。平时流畅对话不发，靠 live+frozen+注意力召回撑住。预算口径同步（breakdown.summary 按 shouldInjectSummary 计；后台塌缩由 10 轮保底兜着，管线不断）。
6. **天气只在首句/resumeGap**（`:2154`）。
7. **诊断日志**：`🧩 [动态注入] session=… blocks=time,weather,attention(n),bridge`（`:2303-2310`）。调 bug 时先看 Zeabur 日志这一行——哪块在注入就是哪块在搞鬼。

**第二批（2026-08-21 晚，外部模型评审后拍板，已部署）**——5 条全部在代码里：
8. **同轮注入上限 3 块**（`dynamicBlocks` + sort/slice，`:2252-2310`）：丢块优先级 想起→残留→天气→时间→桥。resume 轮不再"五件套全塞"。
9. **resumeGap 30→60 分钟**（`:2108`）：去修个 bug/上趟厕所/回个消息（<1h）不再触发"重新进入会话"的重载。
10. **残留收尾抑制**（`:2134`）：她回来第一句话带 `修完|修好|搞定|回来了|解决…` → 残留整体不注入。彻底杀"她都修完了还在催她修 bug"。
11. **想起冷却 3→4**（`:1713`）。
12. **日志加 `last_msg` + `dropped`**：同轮丢了几块、她最后一句是什么，都进同一行日志，方便复盘。

> **诚实边界（GPT 评审指出，写在这）：** 以上把注入块从"她消息紧前面"挪到"live 段开头" + 限数量，解决的是**显著性排序错误**；但注入块**仍是 user 角色**，语义上仍像"她说的话"。没被证明的是**语义权限错误**已解决——模型可能不"抢答"了，但仍被旧话题"语义吸附"（修 bug 在 summary+live+想起+残留各出现一次→它判为重要主题，回话时莫名绕回）。这是当前最大的剩余风险，见 §4.6。

### 4.4 为什么旧文档误导人
`context-assembly.md` §6 红线说「可变内容一律放所有缓存断点之后」——这是对的；但文档正文（§1 示意图）把时间叙事画在「缓存断点之后、当前消息之前」，实现就落到了「她消息紧前面」。这个位置本身没错（缓存安全），但**不是所有注入块都该去那里**——最近 15 轮内的注入块会被当成「刚说的」。**改文档前先改代码里的注释（`:2233`），两处已同步。**

### 4.5 未验证 / 疑点（交接时如实交代）
- 修复是否真正止跳，**待程芥实测**（部署后传播 45-85s）。若还跳，看 `🧩 [动态注入]` 日志定位是哪块。
- **语义权限问题未解决**（最大剩余风险）：注入块仍是 user 角色，只是降了显著性、限了数量；「旧话题语义吸附」仍可能让模型绕回旧话题而不自知。区分三件事：A 抢答旧注入 / B 被旧注入语义吸引 / C 真正丢失最后一轮。测试时别只看"还跳不跳"，要看是哪一种。
- resumeGap 已 60min，但 resume 轮仍是"一整批背景"（摘要+时间+天气+残留），是否该把 resume 做成**独立的精简组装**（只给摘要+时间，不给别的）——见 §4.6 双模式。
- anchorSeg（更老一段摘要）已默认 `null`（按需召回），未验证按需召回够不够。
- 便宜模型对注入纪律的敏感度未知——所有注入纪律都是按「模型会把 user 注入块当她说的话」这个最坏假设设计的。

### 4.6 Context Invariants（不变量） + 双模式 + 回归测试

**① 真正不能破的不变量**（区别"业务不变量"和"实现策略"——只有前者是死线）：
1. 当前真实用户消息必须是 messages 中**最后一个真实 user turn**（注入块不算）。
2. 模型的响应目标永远是**最后一个真实用户消息**，不是任何注入块。
3. 动态注入不能改变历史消息的**语义身份**（历史里"她说的"永远是"她说的"）。
4. **历史数据库永不删除/篡改**——只有这条是业务级死线；frozen 边界不重切只是缓存策略，可调。
5. Context Assembly 可以改变"投影"，不能改变历史事实。
6. **任何召回材料必须有 provenance**（来自哪个语义层）：memory recall / system state / user-provided / conversation history。现在只靠中文前缀标签（【想起】【余温】【登岛来路】…），系统并不知道它们的语义归属——**这是系统最脆的地方**。
7. resume / active 是**两种 context mode**，不是"开几个开关"。

**② 双模式（GPT 提议，尚未实现）**：active 模式 = 流畅对话，除 live+frozen 外尽量零注入；resume 模式 = 精简的"欢迎回来"（摘要+时间，最多加一条收尾抑制后的残留）。现在只是"resumeGap 触发几个开关"，没有真正切成两套组装策略。将来若补丁式收紧不够，这是架构级解法。

**③ 回归测试（两级，都不烧主模型）**：
- **免费级（确定性，现在就能加）**：单元断言「组装结果里最后一条真实 user 消息 = 当前用户消息」；以及「同轮动态块 ≤ 3」。
- **模型级（用 deepseek-v4-flash 便宜档，可选）**：定向场景——当前主题=修bug、旧主题=喝水；历史含"记得喝水/我去修bug"；当前="我修好了"。期望：回应"修好了"、不主动提喝水、不主动建议继续修 bug。测三个指标：**last-user adherence / stale-topic intrusion / background acknowledgement**。

## 5. 改代码前的红线（DO / DON'T）

- ✅ 可变内容（记忆/残留/时间/天气/工具结果）一律放所有缓存断点之后。
- ✅ 注入块必须 user 角色 + 带标记前缀（`【…】`）+ 受【背景纪律】点名。
- ✅ **同轮动态注入 ≤ 3 块**（丢块优先级：想起→残留→天气→时间→桥）。
- ❌ **注入块不许插在「她当前消息紧前面」（liveSection.length-1）**——这是本次 bug 的根源位置。要插就插 live 段开头。
- ❌ 不断点①~②之间注入任何可变内容（缓存失效）。
- ❌ 不删历史、不改历史、不为观察数据加库字段。
- ❌ 缺 `x-client` 头默认当 legacy，永不默认升级成 angel。
- ❌ 不把时间戳放进 system 角色（OpenRouter 会合并进顶层 system 破前缀）。
- ✅ 缓存断点每请求最多 4 个，理想 3 个。
