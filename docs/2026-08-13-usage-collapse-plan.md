# 方案：摘要塌缩改成"按用量触发"

> 写给人：程芥（产品拍板）+ GPT（评审）
> 日期：2026-08-13
> 状态：**GPT 已评审，四个参数全部拍板，架构要求已采纳**（2026-08-13 v2）

---

## 一、先用大白话讲清楚：沈晏现在是怎么"收拾旧账"的

沈晏和用户聊天，对话会越来越长。但模型一次能"看进去"的内容有限，所以沈晏有一套自动整理机制，叫**摘要塌缩**：

- 对话攒到一定程度，系统把**旧的那一截**从原文压缩成一段"摘要"存进长期记忆
- 原文腾出来的位置，留给**最新的对话**看
- 旧的摘要**永不重写**，只往后追加新的摘要段（这是缓存命中的基石，动不得）

这个整理动作，**永远在对话响应结束后后台悄悄做**，不打扰你正在等回复的对话。

## 二、现在的问题：用的是"轮数"这把假尺子

现在的触发规则很朴素：**攒够 8 轮对话，就压一次段**（MIN_SEGMENT_TURNS = 8）。

问题是——轮是长是短差别巨大：

| 情况 | 表现 | 后果 |
|---|---|---|
| 几轮**超长**对话（一大段文字、长回复） | 3 轮就可能接近"模型一眼能看的上限" | 但要等到 8 轮才压 → 上下文挤，可能被迫临时裁掉最近的原文（小缝隙） |
| 8 轮**极短**对话（"嗯""好""知道了"） | 离上限远得很 | 却也压一次 → 白花一次压缩的时间和钱 |

一句话：**轮数是假尺子，真正的尺子应该是"这一轮模型要看多少内容"（用量）。**

## 三、改成什么样：按用量触发（GPT 已拍板）

核心一句话：**"快满才压，没满就不压。"**

### 触发条件（三个一起判断，满足其一就压）

```
用量 ≥ 阈值 (75%)          ← 主触发器：上下文胖了，该收拾了
    或者
轮数 ≥ 10                  ← 保底触发器：用量没到但确实攒够了（GPT 拍板 10 轮）
```

- **阈值**：`max_context_tokens` 的 **75%**（默认 8000 → 用量到 6000 触发）。GPT 意见：不是等"马上爆了才救火"，而是"七成半就开始后台收拾旧账"，剩下的 25% 留给当前用户消息、模型回复、估算误差、动态注入、临时波动。不建议硬提到 85%/90% 去省摘要次数。
- **轮数保底**：从 8 轮改 **10 轮**。主触发器变成用量后，轮数保底只承担"你别真的永远不压"的角色，10 更稳。
- **冷却期**：压完一段后，**至少再攒 4 轮**才允许压下一段（GPT 拍板 4，不是 6）。它只是"防止摘要碎片化的缓冲区"，不是强行延迟——因为有用量阈值 + 10 轮兜底两层，6 轮冷却反而会顶着快满的上下文硬等。

### 用量怎么算：本地估算（GPT 确认第一版用它）

- 用本地估算函数，零依赖、就地可用。不要为了"绝对精确"去接 API 真实用量。
- 理由：我们要判断的是"**下一次请求会不会太胖**"（预判），而 API usage 是"上一轮实际用了多少"（慢一拍）。摘要触发器不需要知道是 5982 还是 6017 token，只需要可靠判断"是不是明显进入危险区了"——75% 阈值本身就在给估算误差留空间。

## 四、架构要求（GPT 评审指出，必须遵守）

> **触发判断必须复用 buildModelContext() 的实际 assembled context / diagnostics，不要维护第二套上下文计算口径。**

原因：现在 Context Assembly（四段组装）已经存在，摘要触发器如果自己再算一遍上下文，两套口径会漂——触发器估 5900，实际组装 7200，判断就全错了。以后改 Frozen/Summary/Live/动态注入，触发器也会跟着漂。

**做法**：

1. `buildModelContext` 组装上下文时，把**裁剪前的原始估算**（以及分段明细）放进返回的 `diagnostics`
2. 响应结束后，`scheduleSummary(sessionId, diagnostics)` 直接把这份估算传给后台摘要任务
3. 后台任务**只读取**这份估算做触发判断，**不自己重算**上下文

一个地方负责组装上下文，一个地方读取它的估算结果。

**已验证可行**：`scheduleSummary` 的两个调用点（流式/非流式响应结束处）同一时刻 `diagnostics` 就在手里，直接传参即可；唯一实现细节是触发要用**裁剪前**的估算值（裁剪后永远 ≤ 上限，会误判为"没满"）。

## 五、怎么验证它真的变好了

加观测（GPT 补充：这些先写日志，不一定全塞 UI）：

- `estimated_context_tokens` — 本次估算总量（裁剪前）
- `threshold_tokens` — 本次阈值（75%）
- `live_tokens` / `summary_tokens` / `frozen_tokens` — 三段各自占了多少
- `trigger_reason` — 触发原因（`usage` / `turns` / `cooldown` / 未触发）

验收三件事：
1. **长对话**：几轮大段文字 → 会自动提前压段（不再挤爆上下文）
2. **短对话**：多轮"嗯嗯"→ 不会频繁压段（不再白花钱）
3. **缓存命中率**：不降反升（因为不再为短对话做无谓的压缩重建）

以后想调优，看到"为什么 4 轮就触发了"→ 日志里 frozen 1800 / summary 2200 / live 1700 / dynamic 400 / total 6100，一眼就知道是这一轮真的胖。

## 六、成本与风险

- **调用成本**：不增加，反而可能减少（短对话少压了，DeepSeek 调用省下来）
- **代码改动范围**：集中在 `buildModelContext`（多吐一个裁剪前估算 + 分段明细）和 `scheduleSummary`/`generateSummaryIfNeeded`（改成读传入的估算做判断），不碰记忆结构、不碰缓存
- **风险**：用量估算本身是估算，可能有 ±20% 偏差 → 阈值留 25% 余量吸收；极端情况有冷却期兜底
