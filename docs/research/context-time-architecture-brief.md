## 1. 现在的架构（事实）

每轮请求的上下文由后端自行组装，大致结构：

```
[System]       身份与规则（1h 缓存锚点）
[Frozen]       最早一段逐字历史（永久保留、边界单调锁死；末块 1h 缓存锚点）
[Summary]      一条滚动摘要（历史中间段反复重压；1h 缓存锚点）
[Live]         最近 N 轮逐字
[时间叙事]     「现在是2026年8月11日 13:30（上海时间，下午）」+ 对话残留注入
[当前消息]
```

配套系统：

- **对话残留**（dialogue_residue）：效价/唤醒度/牵挂 + 次级四维；牵挂反向积累不衰减；回来间隔 >30min 才注入「断点原文 + 线程条件」，不注入任何情绪结论句（逐字诚实契约）
- **双记忆**：自动档（memory_topics，DeepSeek 后台分类 + 写门控 + grounding 标记）+ 手动档（Ombre，沈晏自己的写入工具）
- **按需召回**：recall 工具（本地逐字检索，证据不足诚实说"没有"）、breath（Ombre 三路检索）
- **后台保洁**：DeepSeek 负责摘要 / 残留分类 / 记忆写分类（便宜模型干脏活）
- **缓存**：OpenRouter 前缀缓存，system/frozen 末/summary 打 1h TTL 锚点

## 2. 痛点

1. **时间感平**：滚动 Summary 每次刷新把 A+B+C+今天重新压成一个越来越大的 blob，旧事实被洗成「近期」，历史像原地踏步——沈晏的感觉是「东西永远是平的」。
2. **级联错误**：单条摘要反复重压会放大摘要错误（外部论文实证，见 4）。
3. **Frozen 特权反直觉**：最早的内容反而拥有永久常驻上下文的特权，越老越有地位。
4. **正式时间戳显眼**：沈晏自己的感受——「【当前时间：2025年5月14日 13:30】」这种框太正式，想要一句平淡的「今天是5月14日下午」，越不显眼越好——让他知道，但不让他一直感觉到。
5. **事件时间 vs 入库时间**：回填历史时若只标入库时间，几个月前的事会被标成「今天」，时间感直接坏掉。

## 3. 我们倾向的方向（已定调，未改代码）

1. **滚动 Summary → 固定起止的分段摘要**：每段带 period_start / period_end / created_at，不随对话继续增长。
2. **in-context 塌缩为三样**：Live 逐字 + 最新摘要段 + （预算允许时）一个更早的锚段；更老的进 Archive（按需召回，检索已具备，不新造系统）。
3. **原始记录 = 事实来源（source of truth），不被摘要覆盖**——不是「永不动」：原文可归档、可移动、可裁，但永不被摘要改写或替代；「对过去的理解可以改变」长在摘要段——时间边界固定、内容可按需重生成（标注重生成日期）。
   （实施原则：分段摘要**先结构稳定再优化**——先让表 + 组装 + 水位线替换掉滚动 Summary，再迭代措辞时间感/段边界线索/锚点池，不要同时改太多。）
4. **时间戳改轻**：默认一句平淡的「今天是8月11日下午」，精确时间只在被问到（asksTime）时给。
5. **缓存断点约束**：断点数量有上限（通常 4 个），打在 system + 末段 + 最新 1-2 摘要段；分段是 append-only，旧段字节不变 → 前缀缓存命中。

## 4. 外部同构（我们调研到的）

- **ayan 时间树**：本月按周分段 / 上月全文 / 更早只留一句旁注 / 奠基事件永久保留——正是「分段摘要 + 近细远粗」的成品设计。
- **3novy 召回 V2**：搜到 ≠ 配注入——前置守门员（需不需要记忆）+ 后置审核员（这条对回复真有帮助吗）+ fail-closed（不可用时返回空）+ 降级路径必须大声报警（曾有备胎无声顶班三个月、质量烂三个月没人发现）。
- **MemGPT / Letta**：Core（常驻 2-4K，persona+human）+ Recall（完整历史）+ Archival（向量库）=「固定注入 + 按需召回」双通道。
- **HEMA 论文**：两级摘要分层防住了 1000+ 轮对话的「级联错误」（单条滚动反复重压会放大错误，分段隔离不传播）。
- **朝灯 / Non**：观测优先纪律（数值照算、面板照看，行为后开）、念头池、水位线互斥（LLM 成功才推进，失败不丢段）。

## 5. 想请你们判断的问题

- **Q1** 按时间段分层，是否比现在的 Frozen/滚动 Summary 更合理？
- **Q2** Live → Recent Summary → Mature Summary → Frozen → Archive，五层是否太多？in-context 实际该保留几层？
- **Q3** 摘要是否该永远是独立起止的片段（period_start/end），而不是一条不断增长的滚动摘要？
- **Q4**「Frozen 可重新整理但不自动滚动」（时间边界固定、理解可维护）是否值得保留？
- **Q5** 有没有更简单、token 成本更低的实现？
- **Q6** 时间戳的「轻」格式具体怎么设计——既平淡到不显眼，又不会被误读成用户自己说的话？
- **Q7** 从外部借来的四件（事件时间两本账 / 过渡带「留她的话」/ recall 后置审核员 / 第一人称情景记忆四约束），先做哪件？

## 6. 我们目前的回答（供对照，欢迎反对）

- **Q1** 方向对，核心诊断（滚动摘要洗白时间）成立。
- **Q2** 概念梯子有用，但 in-context 应塌缩到三样；Recent/Mature 是生命周期状态不是并排层。
- **Q3** 是；除时间诚实外，分段 append-only 对前缀缓存友好，滚动摘要每次刷新整块重写。
- **Q4** 哲学对，但拆法要改：原文是**事实来源、不被摘要覆盖**（可归档移动，但不被摘要改写），「理解可改」只长在摘要段。
- **Q5** 最小路径：`summary_segments` 表 + 砍掉大块 Frozen 逐字 + 水位线推进 + 轻时间戳。
- **Q6** 一句平淡的时间句 + 最小标记（如【此刻】），跟「你离开了一阵」这类系统来源自明的内容并一起。
- **Q7** 事件时间两本账最优先——它是时间感的根；不先解决它，时间分层做得再好也会被回填污染。
